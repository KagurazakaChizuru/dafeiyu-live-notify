## 1. 问题定义

主播每次开播都要手动往若干个 QQ 群里发一条 `@全体成员` 通知，重复、易漏、且必须在开播那一刻及时发出。

直觉方案是「监控直播软件的进程，检测到就发」。**这个方案有本质缺陷：**

> 打开直播软件 ≠ 开播。

OBS / 直播姬 / 直播伴侣 从启动到真正推流之间，通常隔着几分钟的设备调试、试麦、试妆、调灯光。如果在这个窗口发通知，群友会先收到一条无效提醒，然后干等——**这比不发更糟**。

因此本项目的第一条设计原则是：

> **只在「用户真正按下开播」的时刻触发。**

这条原则直接决定了整个触发子系统的设计（见 §5）。

### 第二个问题：NapCat 会占用用户自己的 QQ

NapCat 默认启动注册表里那个 QQ 安装。QQ 桌面端是单实例的，结果是：通知器一开，用户自己的 QQ 就用不了了。

本项目通过「独立 QQ 副本」解决（见 §6）。

## 2. 目标与非目标

### 目标

| 编号 | 目标 |
|---|---|
| G1 | 精确捕获「开始推流」时刻，而非「软件启动」时刻 |
| G2 | 覆盖没有开放接口的直播软件（B站直播姬、抖音直播伴侣） |
| G3 | 通知器常驻时，用户自己的 QQ 照常可用 |
| G4 | 零第三方运行时依赖（仅 Python 标准库 + tkinter） |
| G5 | 可视化配置，非技术用户可用 |
| G6 | 可打包为免安装单文件 exe |
| G7 | 全本地通信，不向任何第三方上报 |

### 非目标

- 不做直播内容的录制、转推、弹幕处理
- 不做跨平台（仅 Windows，因为依赖 Win32 进程枚举与 `RegisterHotKey`）
- 不绕过 QQ 的 `@全体成员` 权限限制（那是平台侧规则）
- 不内置 QQ 或 NapCat 的分发（见 §15）

## 5. 触发子系统

### 5.1 触发源规格

#### 5.1.1 PlatformWatcher —— 直播间状态轮询（首选）

| 项 | 规格 |
|---|---|
| 数据来源 | `GET https://api.live.bilibili.com/room/v1/Room/get_info?room_id=<id>` |
| 鉴权 | **无需**登录 / 签名 / cookie |
| 关键字段 | `data.live_status`：`0`=未开播，`1`=直播中，`2`=轮播 |
| 轮询间隔 | 默认 30 秒（可配 5 ~ 3600） |
| 房间号来源 | 优先 `trigger.room_id`；留空则从 `message.link` 正则提取 |
| 网络策略 | **默认直连，不走系统代理**（见 §11.3 T9） |

**为什么它是首选的触发源**：它是唯一**与开播软件无关**的信号。
不管用户用 OBS、直播姬、直播伴侣，还是干脆用手机开播，只要房间真的开了就能检测到；
而且读到的是**平台判定的真值** —— 群友要知道的正是「房间开了」，
而不是「用户点了某个按钮」（这两者可能因推流失败、断流而不一致）。

**状态机规格**：

```
state ∈ {unknown, live, offline}        初始 unknown

收到 live_status == 1：
    state == offline  →  触发 on_live，state := live
    state == unknown  →  **不触发**（启动时已在直播不补发），state := live
    state == live     →  无动作

收到 live_status == 0：
    state == live     →  记录 offline_since；持续 ≥ offline_grace 后触发 on_offline
    state == offline  →  无动作（不重复报下播）

收到 live_status == 2（轮播）：
    按离线处理，但**不触发** on_offline —— 轮播本来就不是用户在播
```

**四条防打扰设计**（每条都对应一种会被用户投诉的行为）：

| 设计 | 防止的问题 |
|---|---|
| 只在状态跳变时触发 | 直播期间反复发通知 |
| 启动时已在直播不补发 | 每重启一次程序，群友就多收一条 |
| 离线宽限期（默认 60 秒） | 断流重连被误判为下播 |
| 轮播不触发下播 | 自动重播被误判为「播完了」 |

**时长计算**：优先解析接口的 `live_time` 字段（形如 `2026-09-17 22:30:00`）；
为 `0000-00-00 00:00:00`（离线占位）或解析失败时，退回使用本地观测到的进入直播时刻。

#### 5.1.2 ObsWatcher —— OBS 推流事件

| 项 | 规格 |
|---|---|
| 协议 | obs-websocket 5.x |
| 连接 | `ws://127.0.0.1:<port>/`，默认端口 4455 |
| 凭据来源 | 自动读取 `%APPDATA%\obs-studio\plugin_config\obs-websocket\config.json` |
| 用户配置成本 | **零**（端口与密码均自动获取） |
| 订阅 | `eventSubscriptions = Outputs(1<<6) \| General(1<<0) = 65` |
| 触发条件 | `eventType == "StreamStateChanged"` 且 `eventData.outputActive == true` |
| 重连 | 断线后 8 秒重试；OBS 未运行时每 20 秒探测一次配置 |
| 辅助校验 | 连接建立后发 `GetStreamStatus` 请求，捕获「连上时已在推流」的情况 |

**认证算法**（obs-websocket 5.x）：

```
secret   = base64( sha256( password + salt ) )
auth     = base64( sha256( secret + challenge ) )
```

**WebSocket 客户端**：标准库无 WebSocket，故自行实现（`WsClient`），支持：
- HTTP Upgrade 握手与 `Sec-WebSocket-Accept` 校验
- 帧解析（FIN/opcode/掩码/126·127 扩展长度）
- 自动应答 ping、主动发送 close
- 通过 socket 超时抛 `WsIdle`，使主循环能周期性检查停止标志

#### 5.1.3 HotkeyListener —— 全局热键（通用兜底）

| 项 | 规格 |
|---|---|
| 机制 | Win32 `RegisterHotKey` + `PeekMessage` 消息泵 |
| 默认值 | `ctrl+alt+k` |
| 格式 | `修饰键+键`，修饰键 ∈ {ctrl, alt, shift, win}，键 ∈ 字母/数字/F1–F24 |
| 必须含修饰键 | 是（防止误触） |
| 注册失败处理 | **必须**在界面与日志中明确提示并给出可用替代值 |

> **为什么需要它**：B站直播姬虽然是 OBS 内核，但**未附带 obs-websocket 插件**；抖音直播伴侣完全封闭。这两个软件无法程序化检测开播时刻。

#### 5.1.4 TriggerEngine —— 进程检测（默认关闭）

| 项 | 规格 |
|---|---|
| 匹配方式 | 进程名小写子串匹配 |
| 防抖 | 连续命中 `confirm_checks` 次（默认 2）才触发 |
| 重新武装 | 进程消失后持续 `stop_grace_seconds` 秒（默认 60）才恢复可触发 |
| 默认状态 | **关闭**（`on_process_start: false`），原因见 §1 |

**状态机**：

```
                    ┌──────────────┐
      初始 ────────►│   已武装      │
                    └──────┬───────┘
                           │ 连续命中 ≥ confirm_checks
                           ▼
                    ┌──────────────┐
                    │   已触发      │──── 调用 fire()，由闸门判定是否真发
                    └──────┬───────┘
                           │ 进程消失
                           ▼
                    ┌──────────────┐
                    │  等待重新武装  │
                    └──────┬───────┘
                           │ 消失持续 ≥ stop_grace_seconds
                           └──────► 回到「已武装」
```

#### 5.1.5 控制端口（手动触发）

见 §8.3。任何情况下都可作为最后手段。

#### 5.1.6 UpWatcher —— UP 主新投稿轮询（1.8.0）

| 项 | 规格 |
|---|---|
| 数据来源 | `GET https://api.bilibili.com/x/space/wbi/arc/search?mid=<uid>` |
| 鉴权 | **无需登录**，但要凑齐 wbi 签名 + buvid 指纹 + 探针参数，见下 |
| 关键字段 | `data.list.vlist[].created`（epoch 秒）、`bvid`、`title` |
| 轮询间隔 | 默认 300 秒，**下限 60 秒**（`subscribe.poll_seconds`） |
| 状态文件 | `logs/subscribe-state.json`，每个 UP 主一条 `last_created` |
| 实现 | `bili.py`（纯标准库，只读；`live_notify.poll_subscriptions()` 负责判断） |

匿名读取要凑齐三样东西，缺一样就拿到一个看不懂的码：

1. **wbi 签名** —— `x/web-interface/nav` 取 `img_key` / `sub_key`，按 64 项混淆表
   重排取前 32 字当密钥；参数按 key 排序、连 `wts` 一起 MD5 得 `w_rid`。
2. **buvid 指纹** —— `x/frontend/finger/spi` 取 `buvid3` / `buvid4`，随 Cookie 发。
3. **`dm_img_*` 探针参数** —— 值是占位符，接口只校验它们"存在且像个样"。
   缺这组会拿到 `-352`，而错误文案完全看不出是这个原因。

**两条纪律**（`_selftest.py` 第 16 组里各有一条断言钉住）：

- **首次见到某个 UP 主只记基线，一条都不播报。** 状态里没有记录 = 第一次见 ——
  否则刚订阅就把人家几年的旧投稿刷进群里，这是这类功能最典型的失败方式。
- **按发布时间（`created`）比对，不按"在列表里的位置"。** 列表随翻页滚动，位置会变。

积压超过 3 条时只播报最新一条并记一行 WARN。撞上任何风控码（`-352` / `-799` / `412`）
**就退避 15 分钟**（`SUB_BACKOFF_SECONDS`）：退避时刻记在状态文件里，这段时间一个请求
都不发。原实现是撞上之后照 `poll_seconds` 的节奏接着敲 —— 那等于把封禁往外拖。
（请求头的坑见 §11.3 T17，频率的坑见 T18。）

### 5.2 冷却闸门

**问题**：多个触发源可能同时命中（例如在 OBS 里点开播的同时又按了热键），导致重复发送。

**规格**：所有触发源共用一个 `CooldownGate`：

```
fire(reason):
    allowed, remain = gate.allow(mark=True)   # 放行 + 记账，同一把锁里做完
    if not allowed:
        log("触发（reason），但还在冷却期，还剩 remain 秒，跳过")
        return False
    send_to_groups(reason)
    return True
```

**`mark=True` 不是可选的写法。** 老实现是 `allow()` 再 `mark()` 两次调用，
两次调用之间别的触发源也能通过 `allow()` —— "在 OBS 里点开播 + 顺手按了快捷键"
同时到达时两边都放行，群里收两遍。`_selftest.py` 第 4 组里有一条真开 8 个线程
抢闸门的断言钉住它，另有一条静态断言禁止调用点退回两步写法。

冷却时长由 `behavior.cooldown_minutes` 控制，默认 30 分钟；设为 `0` 则关闭冷却。

### 5.3 触发语义矩阵

| `on_platform_live` | `on_obs_stream` | `hotkey` | `on_process_start` | 实际行为 |
|---|---|---|---|---|
| true | true | 有 | false | **推荐配置**：全自动，三种信号互为补充 |
| true | false | 空 | false | 完全靠直播间轮询（与开播软件无关） |
| false | true | 有 | false | OBS 全自动；直播姬/直播伴侣靠热键 |
| false | false | 有 | false | 全部靠热键 |
| true | true | 有 | true | 四者并存（进程检测会误报，不推荐） |
| false | false | 空 | false | 只能通过控制端口手动触发（界面会告警） |

### 5.4 下播通知的独立闸门

**这是必须的，不是可选项。**

开播侧有 `behavior.cooldown_minutes`（默认 30 分钟）的冷却，用于防止同一次开播被多个
触发源重复通知。但**下播通知不能共用这个闸门** —— 否则用户只播了 10 分钟就下播时，
下播通知会被开播那 30 分钟冷却静默吃掉，表现为「下播提示时有时无」。

因此下播使用独立的 `offline_gate` —— 源码里就是 `triggers.CooldownGate(0)`，
**冷却写死为 0、不看配置**，并由以下机制防止刷屏：

1. 只在 `live → offline` 跳变时触发（持续离线不重复）
2. `offline_message.grace_seconds` 离线宽限期（默认 60 秒）
3. `live_status == 2`（轮播）直接不触发

**下播消息的发送参数**与开播通知不同：

| 参数 | 取值 |
|---|---|
| `template` | `pick_from(offline_message.templates, offline_message.template, kind="offline")` |
| 额外占位符 | `{duration}`（本次时长）、`{peak}`（本场人气峰值，为 0 时传空串以便删行）、`{game}`（最后在玩的） |
| `at_all` | `offline_message.at_all`（**默认 false**） |

> 下播默认不 @ 任何人：没在看直播的人不会关心你几点停播。
> 若为 true，则覆盖所有群的 `at_all` 设置，统一 @全体成员。

## 6. 会话共存设计（独立 QQ 副本）

### 6.1 问题

NapCat.Shell 的官方启动器从注册表读取 QQ 安装路径并启动它。QQ 桌面端同一时间只允许一个实例，因此 NapCat 运行期间用户的 QQ 不可用。

### 6.2 方案

**利用 Windows 按可执行文件路径区分应用的特性**，为 NapCat 提供一份**独立路径**的 QQ：

```
app/
├── napcat/                      NapCat 本体
│   ├── launcher-user.bat        官方启动器：查注册表 → 系统 QQ（会占用）
│   ├── launcher-second.bat      本项目：直指私有副本 → 独立实例（不占用）
│   └── launcher-hidden.bat      同上，但无 pause，供 CREATE_NO_WINDOW 使用
├── _fix-qq-link.ps1             启动前修复版本目录联接（见 6.3）
└── qq-napcat-private/           私有副本，实测 7.6 MB
    ├── QQ.exe  QQEX.exe  *.dll  真实文件（约 8 MB）
    └── versions/
        ├── *.json               真实文件（QQ 会写这几个）
        └── <ver>/               ← **目录联接（junction）**，指向系统 QQ 的同名目录
```

`launcher-second.bat` 与官方启动器的唯一区别：跳过注册表查询，直接

```
set "QQPath=%~dp0..\qq-napcat-private\QQ.exe"
```

### 6.3 为什么是联接而不是整份拷贝

QQ 的 `versions/<ver>/` 有 1.1 GB，而且装完之后**几乎不再被写入**（实测：系统 QQ 的版本目录自安装日起一周内零改写）。整份拷贝等于白白复制一份 Electron 运行时。

所以只保留顶层那 8 MB 真实文件，版本目录用 **junction** 指向系统 QQ 的同名目录。判定"是不是第二个实例"看的是 **exe 的路径**，而 `qq-napcat-private\QQ.exe` 是真实文件、路径不同，因此仍然被 Windows 当成另一个应用。

**代价：这份副本不再是自包含的** —— 换一台机器必须先把 QQ 装在同一个位置。
这是用 1.1 GB 换来的，权衡后认为值得（部署文件夹从 1204 MB 降到约 41 MB）。

> QQ 每次自我更新都会装出一个**新的版本目录**，旧的随后被删掉，届时联接就会悬空、
> NapCat 直接起不来。所以两个启动器在拉起 NapCat 之前都会先跑一次
> `_fix-qq-link.ps1`：它从注册表找到系统 QQ，取最新的版本目录，发现联接指错就
> 用 `rmdir` 删掉旧联接（**只删链接，不会碰目标内容**）再重建。QQ 升级因此变成无感事件。

### 6.4 验证结论（实测）

```
启动前：用户 QQ  16 个进程
启动后：用户 QQ  16 个进程（全部存活）+ 私有副本 4 个进程
        OneBot get_login_info 正常返回
停止后：用户 QQ  16 个进程
```

### 6.5 停止语义（关键安全约束）

`stop_napcat()` **必须**只终止副本实例。实际逻辑（`gui.py`，以源码为准）：

```
1. taskkill /IM NapCatWinBootMain.exe /F
2. 若 napcat/launcher-second.bat 在（= 私有副本模式）：
     仅终止 ExecutablePath 含 "qq-napcat" 的 QQ.exe 进程
     （Get-CimInstance Win32_Process 过滤，绝不用 taskkill /IM QQ.exe）
   否则（没生成副本，退回官方启动器）：
     taskkill /IM QQ.exe /F   ← 会把用户自己的 QQ 一起关掉
```

> 第 2 步那个 `else` 分支**是有意的退路，也是这条约束的边界**：
> 没有私有副本时，NapCat 和用户的 QQ 是同一个实例，关了 NapCat 就必然关掉它。
> 所以"不碰用户的 QQ"这句话的完整前提是「已经跑过 `_setup-qq-copy.ps1`」。
>
> **另外它只在启动时判一次**：`launcher-second.bat` 存在与否是在 `stop_napcat()`
> 被调用那一刻查的，所以"服务跑起来之后才生成副本"这种情况不走私有副本分支。

> 私有副本的目录名特意保留 `qq-napcat` 字样（`qq-napcat-private`），
> 这样 `-like '*qq-napcat*'` 这个过滤条件不用改也能同时匹配新旧目录名。

> 早期实现使用 `taskkill /IM QQ.exe /F`，会连带杀掉用户自己的 QQ。这是本项目最严重的一次缺陷。
> **代码已经改成按路径过滤，但这条修正目前没有测试覆盖** —— `_selftest.py` 里没有任何
> `stop_napcat` 相关的用例，§12.3 那份关键回归项清单里它也只是"必须手动验"。
> 换句话说：这条安全约束靠的是每次改 `gui.py` 的人自己记得去跑一遍，
> 而不是靠自检拦住。谁哪天补上这个用例，这里的措辞就可以改回去了。

## 7. 通信接口规格

### 7.1 OneBot v11（HTTP）

`POST {base_url}/{action}`，`Content-Type: application/json`，可选 `Authorization: Bearer <token>`。

| Action | 请求体 | 使用的响应字段 |
|---|---|---|
| `get_login_info` | `{}` | `data.user_id`、`data.nickname` |
| `get_group_list` | `{}` | `data[].group_id`、`group_name`、`member_count` |
| `get_group_member_info` | `{group_id, user_id}` | `data.role` |
| `get_group_member_list` | `{group_id}` | `data[].user_id`、`role` |
| `send_group_msg` | `{group_id, message[]}` | `data.message_id` |

**响应判定**：`status == "ok"` 或 `retcode == 0` 视为成功。

> **强制约束**：HTTP 客户端**必须**显式禁用系统代理。
> `urllib` 默认读取 Windows 注册表代理设置，会把发往 `127.0.0.1` 的请求也交给代理，表现为代理返回 `502 Bad Gateway`，看起来像 NapCat 挂了。实现中使用 `build_opener(ProxyHandler({}))`。

### 7.2 obs-websocket 5.x

| op | 方向 | 载荷 |
|---|---|---|
| 0 | S→C | `Hello`：`{obsWebSocketVersion, rpcVersion, authentication?}` |
| 1 | C→S | `Identify`：`{rpcVersion, authentication?, eventSubscriptions}` |
| 2 | S→C | `Identified` |
| 5 | S→C | `Event`：`{eventType, eventIntent, eventData}` |
| 6 | C→S | `Request`：`{requestType, requestId}` |
| 7 | S→C | `RequestResponse`：`{requestType, requestStatus{code}, responseData}` |
| 9 | S→C | `Identify` 失败（认证错误） |

本项目使用的事件：`StreamStateChanged`；使用的请求：`GetStreamStatus`（`requestStatus.code == 100` 表示成功）。

### 7.3 本地控制端口

绑定 `127.0.0.1`（**不可**绑定 `0.0.0.0`），默认端口 8899。

| 路径 | 方法 | 说明 |
|---|---|---|
| `/` | GET | 极简 HTML 页面，一个手动触发按钮。**唯一不需要凭据的一条** |
| `/status` | GET | JSON 状态：`armed`、`trigger_sources`、`obs`、`hotkey_ok`、`groups`、`last_fire`。**需要凭据** |
| `/health` | GET | 与 `/status` 同一份内容。**需要凭据** |
| `/trigger` | GET | 手动触发一次。**需要凭据** |

> **鉴权口径（2026-09-19 起）**：设了 `control.token` 之后，除 `/` 之外全都要带
> 凭据，优先 `Authorization: Bearer <token>`；`?token=` 只作兼容，用一次提示一次
> （见 §5.2）。**token 留空时行为不变** —— 一律放行，默认配置不受影响。
>
> `/status` 以前是免鉴权的，理由是界面轮询走的是裸请求，加了界面就看不到触发源
> 状态。可它会带出**群号、当前在玩什么、直播间标题**；端口虽然只绑 `127.0.0.1`，
> 本机任何程序都读得到，和 `/trigger` 本是同一个级别。现在界面轮询会自己带上
> `Authorization` 头，两边一起改了。

>
> 1. **`game.change_cooldown_minutes` 默认是 `0`，不是 5。** 代码那行旁边写着原因：
>    冷却放这里会压掉"玩 A 几分钟换 B"这种正常行为，群里还以为你在玩上一个。
>    防抖是另一件事，交给 `change_settle_seconds`（默认 20 秒）。
>    1.7.5 之前这两件事混成了一个 `change_cooldown_minutes: 5`，已被拆开 —— 见 §16.4。
> 2. **`ui` 段必须原样带出去。** GUI 保存设置时是把 `self.cfg` 整个 dump 回文件的；
>    这个 dict 里要是没有 `ui`，任何一次"保存"都会把主题偏好从 `config.json` 里抹掉，
>    表现是"保存 → 重启"之后回落浅色。
>
> 另外：`message.templates` / `message.hooks` / `offline_message.templates` /
> `reminder.templates` / `game.change_templates` / `subscribe.templates`
> 这六个池子**留空不是"没有文案"**，
> `load_config()` 会回填内置池（`TEMPLATE_POOLS` / `HOOK_POOL`）。
> 用户自己写的那条会被 `_own_first()` 插在池子最前面，不会被内置文案盖掉。
>
> **还有两个"代码默认值 ≠ 示例值"的地方**，容易被当成默认值抄走：
>
> | 键 | `load_config()` 的默认值 | 这里写 true 的原因 |
> |---|---|---|
> | `trigger.on_platform_live` | **`false`** | 它是首选触发源，`config.example.json` 和界面推荐都开成 true。真正没填这个键时，代码是不开轮询的 |
> | `trigger.hotkey` | **`""`（空串 = 禁用热键）** | `ctrl+alt+k` 是示例配置和界面默认值 |
>
> 换句话说：**这份 Schema 抄的是 `config.example.json`，不是 `load_config()` 的兜底值。**
> 两者在 `on_platform_live` / `hotkey` 上不一致，以代码为准的那一列已在上表标出。

### 8.3 配置文件读取约束

**必须**以 `utf-8-sig` 读取。记事本等编辑器会写入 UTF-8 BOM（`EF BB BF`），普通 `utf-8` 读取会把 BOM 当作 JSON 内容的第一个字符而解析失败。

### 8.4 消息模板占位符

**以 `live_notify.py` 的 `ALLOWED_PLACEHOLDERS` 为准，一共 13 个。**
"运行时取值来自哪里"看同一文件 `render_text()` 里 `fields` 的构造 —— 两处必须一致，
不一致的后果是用户看到一个"写着不报错、发出去却是花括号"的占位符。

| 占位符 | 展开为 | 值从哪来 | 空值时 |
|---|---|---|---|
| `{title}` | 配置里写死的那句标题 | `cfg["message"]["title"]` | 删掉整行 |
| `{link}` | 直播间地址 | `cfg["message"]["link"]` | 直接渲染（不看空） |
| `{time}` | 当前时间 `HH:MM` | `datetime.now().strftime("%H:%M")` | 不可能为空 |
| `{date}` | 当前日期 `YYYY-MM-DD` | `datetime.now().strftime("%Y-%m-%d")` | 不可能为空 |
| `{hook}` | 群文案（开场白那句） | `cfg["message"]["hooks"]` 里随机挑一条 → `random.choice` | 留空则回落到内置 `HOOK_POOL`，基本不会空 |
| `{game}` | 正在玩的游戏 | `extra_fields["game"]`，来自 `games.detect()`；开播 / 提醒 / 下播 / 换游戏四处各传各的 | 删掉整行 |
| `{duration}` | 本场直播时长 | `triggers.format_duration()`，下播时算；传空时统一显示"一会儿" | 有兜底，不会空 |
| `{peak}` | 本场人气峰值 | `PlatformWatcher.peak_online`（轮询时逐次取 `BilibiliRoom.online()` 的最大值） | 删掉整行 |
| `{prev_game}` | 换游戏前的上一个游戏 | 换游戏时把 `state["game"]` **先存后覆盖**，作为 `extra_fields["prev_game"]` 传进去 | 认不出来时是空串，但含它的模板会被 `pick_from(avoid=...)` **整条排除**，见 §16.3 |
| `{tod}` | 时段词（凌晨/早上/上午/中午/下午/晚上/深夜） | `time_words()`，**挑文案那一刻**按当前小时算 | 不可能为空 |
| `{weekday}` | `星期一` … `星期日` | 同上，`time_words()` | 不可能为空 |
| `{room_title}` | B站上**真实的**直播间标题 | `PlatformWatcher.room_title()` → `BilibiliRoom.room_title()` 读接口的 `data.title` | 删掉整行 |
| `{room_desc}` | 直播公告（已剥 HTML） | `PlatformWatcher.room_desc()` → `BilibiliRoom.room_desc()` 读 `data.description`，剥标签、还原实体、压空白、软截断 120 字 | 删掉整行 |

> `{title}` 和 `{room_title}` **不是一回事**：前者是配置里写死的，后者是你此刻在直播间的标题。
> `{room_title}` / `{room_desc}` 这两个函数一直存在，但 1.7.5 之前从没被调用过（见 §16.5）。

模板格式错误时降级为字面替换并告警，不中断发送。
"写成 `{titel}` 这种不认识的占位符"会在 `check` 里被列出来，渲染时由 `scrub_template()` 整对删掉。

## 9. 消息构造规格

### 9.1 消息段数组

```jsonc
// at_all = true
[
  {"type": "at",   "data": {"qq": "all"}},
  {"type": "text", "data": {"text": " "}},
  {"type": "text", "data": {"text": "<渲染后的模板>"}}
]

// at_all = false, at_list = [10001, 10002]
[
  {"type": "at",   "data": {"qq": "10001"}},
  {"type": "text", "data": {"text": " "}},
  {"type": "at",   "data": {"qq": "10002"}},
  {"type": "text", "data": {"text": " "}},
  {"type": "text", "data": {"text": "<渲染后的模板>"}}
]

// 都不启用
[
  {"type": "text", "data": {"text": "<渲染后的模板>"}}
]
```

> **规格要求**：每个 `at` 段后**必须**紧跟一个空格 `text` 段。QQ 不会自动在 `@` 后补空格，否则会渲染成 `@全体成员我开播啦`。

### 9.2 群权限判定

`@全体成员` 仅在发送者身份为**群主或管理员**时真正生效。普通成员发送后消息会显示，但不会提醒到人。

**角色查询采用两段式**（`resolve_role()`）：

```
1. 调用轻量的 get_group_member_info
2. 若结果为 owner/admin —— 采信，结束
3. 若结果为 member（不利结果）—— 用 get_group_member_list 全量列表复核
4. 复核仍找不到该成员 —— 返回 member
```

> **原因**：NapCat 刚登录、群成员缓存尚未加载完成时，`get_group_member_info` 会返回未初始化的默认值 `member`，导致程序误判「无管理员权限」，进而错误地把 `at_all` 关闭。本项目曾因此实际影响用户配置。

### 9.3 发送策略

- 按 `groups` 顺序逐个发送
- 群之间间隔 `behavior.send_interval_seconds` 秒（防风控）
- 单个群失败不中断其余群，逐群记录结果，最后汇总成功数
- 汇总信息包含 `message_id`，便于在群里核对

### 9.4 占位符与"整行消失"

可用占位符分为两类：

| 来源 | 占位符 | 何时有值 |
|---|---|---|
| 来源 | 占位符 | 何时有值 |
|---|---|---|
| 配置 | `{title}` `{link}` | 总是 |
| 配置（池子留空则回落到内置池） | `{hook}` | 总是（内置 18 条） |
| 计算 | `{time}` `{date}` `{tod}` `{weekday}` | 总是 |
| 运行时 | `{game}` | 识别到游戏时 |
| 运行时 | `{room_title}` `{room_desc}` | 直播间轮询开着、且接口取到了值时 |
| 运行时 | `{duration}` | 下播提示时（空则显示"一会儿"） |
| 运行时 | `{peak}` | 下播提示时，且本场人气峰值 > 0 |
| 运行时 | `{prev_game}` | 换游戏播报、且认得出上一个游戏时 |

完整 13 个占位符及各自的取值来源见 §8.4。

**关键规则：`{game}` / `{peak}` 没值时，把它所在的整行删掉** —— 名单在
`live_notify.DROP_LINE_WHEN_EMPTY`，实际是 5 个：`game` `peak` `room_title` `room_desc` `title`。

不这么做的话，模板「正在玩《{game}》」在没识别出游戏时会渲染成
「正在玩《》」—— 一条残句比没有这一行难看得多。实现见
`live_notify._drop_empty_lines()`：删行后还会压掉因此产生的连续空行。
万一整条消息被删空了，会退回未删行的版本，绝不发出空消息。

> `{prev_game}` **不走这条规则** —— 删行会把「不玩《{prev_game}》了」整句干掉，
> 什么都不剩。它走的是 `pick_from(avoid=("prev_game",))`：认不出上一个游戏时，
> 含这个占位符的模板**整条被排除**。两种机制的区别见 §16.3。

### 9.5 游戏名识别

通知里写清楚"正在玩什么"，比单说"开播了"有说服力得多。`games.py`
用五层依次尝试，**任意一层命中就停**：

| 层 | 来源 | 说明 |
|---|---|---|
| 1 | `game.names` | 配置里的手工映射，最高优先 |
| 2 | 场景字典 | 直播姬 / OBS 场景文件里 `game_capture` 源绑定的窗口 |
| 3 | 平台库 | Steam `appmanifest` / WeGame `rail_apps` 的安装目录 |
| 4 | 窗口标题 | 清洗后直接当名字用 |

> **第 5 层「读 exe 版本信息」没有实现**，也不打算做了：反作弊游戏进程受保护、
> 连 exe 路径都读不到，而这层最需要它；读得到的那些游戏，第 2/4 层早就命中了。
> 收益太低。认不出来的游戏请写进 `game.names`。

**为什么不是 OCR。** 实测过：窗口标题就够了。

```
DeltaForceClient-Win64-Shipping / UnrealWindow / "三角洲行动"
```

OCR 要截图、会认错字、还得把屏幕内容送去识别，代价远大于收益。

#### 9.5.1 场景字典是最划算的一层

直播姬和 OBS 的场景文件里，每个游戏捕获源都记着它绑定的窗口：

```json
{"id": "game_capture",
 "name": "战争雷霆",
 "settings": {"window": "War Thunder:DagorWClass:aces.exe"}}
```

格式是 `<窗口标题>:<窗口类>:<exe名>`。**这等于一份主播自己维护出来的
游戏清单**，白捡的。两个细节：

- 只认 `game_capture`。`window_capture` 是抓浏览器、剪辑软件的，
  索引进去会认出一堆不是游戏的东西（实测混进过 Chrome、必剪）。
- 源名可能是"游戏进程 3"这种通用名，这时改用窗口标题。
  优先级 2（主播起的源名）永远压过优先级 1（窗口标题），
  跟扫描顺序无关。

#### 9.5.2 窗口打分

不是"哪个游戏在跑"，而是"哪个窗口像在玩的游戏"。逐项累加：

| 条件 | 分 |
|---|---|
| 命中手工映射表 | +120 |
| 窗口类属于 `GAME_WINDOW_CLASSES`（`UnrealWindow` / `UnityWndClass` …） | +60 |
| exe 在字典里 / 路径命中平台安装目录 | +50 |
| 面积 ≥ 屏幕 70% | +25 |
| 进程工作集 > 800 MB | +20 |
| 是前台窗口 | +15 |

阈值 55：窗口类是游戏、或被字典认识 + 全屏，都能过；而一个全屏的
浏览器只有 25 分，会被挡掉。

> **不能用"只看前台窗口"**：主播切出去聊天时，前台就变成浏览器了，
> 会误判成没在玩游戏。所以是遍历全部可见窗口再挑分最高的。

#### 9.5.3 实测踩到的脏数据

- **零宽字符**：某些启动器会把标题写成 `C​a​l​l​ ​o​f​ ​D​u​t​y`，
  每个字母之间插一个 U+200B。不清洗的话群里会收到一串看不见的乱码。
- **书名号**：`《战舰世界》` → `战舰世界`，否则渲染成「正在玩《《战舰世界》》」
- **商标符号**：`FarCry®6`、`Call of Duty™`
- **反作弊游戏读不到 exe 路径**：三角洲这类进程受保护，非管理员拿不到
  `QueryFullProcessImageName`。所以第 3 层对它们无效，**第 4 层窗口标题
  才是不可替代的**。

#### 9.5.4 换游戏播报

直播中每 15 秒重新识别一次（`cmd_watch()` 主循环里的 `next_aux`，跟进程检测那个 5 秒节奏分开跑），
名字变了就补发一条（默认不 @ 任何人）：

- **平台轮询开着的时候**才拿它确认"确实还播着"（`platform.state == "live"`），
  白天开着游戏不会往群里发。平台轮询没开、或者没解析出房间号时**不能拿它当闸门** ——
  否则只用 OBS / 进程检测的人永远收不到换游戏播报，连二次提醒也一起没有，
  而且一声不响（2026-09-19 修）
- 新名字要先稳定 `game.change_settle_seconds`（默认 20 秒）才播报 —— 这一层管的是
  "这游戏是不是**真的**换了"（切窗口、加载地图会让标题瞬间变）
- 两条播报之间还有 `game.change_cooldown_minutes`（**默认 0，即不拦**）——
  这一层管的是"两条播报别挨得太密"，不是防抖

> **默认 0 是有意的。** 只有冷却没有确认时间的那一版，会把"玩 A 几分钟换 B"
> 这种正常行为当刷屏压掉，群里还以为你在玩上一个。两件事的分工见 §16.4。

### 9.6 封面小图

开播通知里附一张直播封面，整条消息在群里会显眼很多。

**不需要下载、不需要缩放、不依赖 Pillow**：B站图床支持在 URL 后面缀
缩放参数，由 CDN 直接切好返回。

```
原图                                    155 KB
@200w_112h_1c.webp                        6.4 KB
```

消息段就是普通的 image 段，`file` 直接填这个地址，NapCat 自己去取：

```json
{"type": "image", "data": {"file": "https://i0.hdslb.com/...@200w_112h_1c.webp"}}
```

封面**附在文字后面**。放最后是有意的：文字连同链接先入眼，封面跟在后面
把整条消息撑大。取不到封面时静默跳过，消息照发。

## 10. 界面规格

### 10.1 主界面

顶部状态区分成两块，都从底层真实状态取，不做乐观显示：

```
                                    ☾ 深色            未开启
● QQ 已就绪　示例机器人（10001）
触发源　直播间 未开播　·　OBS 未连接　·　快捷键就绪
```

- 第一行是 NapCat 连接态，`_poll_health` 每 8 秒刷一次；连不上就变红
- `触发源` 那一行由 `_poll_trigger` 每 4 秒拼一次，把"一个都没启用"这种致命配置
  直接写成告警，而不是留一行空的

**整个界面只有一个主按钮，钉在最底下那条常驻栏里**（`_set_state()` 管它的三态）：

| 状态 | 按钮文字 | 背景色 |
|---|---|---|
| 空闲 | 开始直播通知 | 蓝 |
| 进行中 | 请稍候 … | 灰（禁用） |
| 运行中 | 停止监控 | 红 |

按钮左边是**快捷键提醒条**（`_refresh_hotkey_hint()`），三态 ——
措辞跟"按不按快捷键"无关：有直播间轮询之后快捷键只是备用手段，
所以语气写的是"可手动推一次"，而不是"必须按"：

| 条件 | 显示 | 颜色 |
|---|---|---|
| 开了自动检测（直播间 / OBS 任一） | `已开启自动检测（直播间开播 + OBS 推流）`，外加一句"快捷键 X 可手动推一次" | 绿 |
| 没开自动检测、但热键可用 | `⚠ 没开自动检测，开播要手动按 CTRL+ALT+K` | 黄 |
| 两个都没开 | `⚠ 自动检测和快捷键都没开，开播不会通知任何人` | 红 |

### 10.2 标签页

| 标签 | 内容 |
|---|---|
| 运行日志 | 深色终端风格，滚动上限 1500 行，含 NapCat 转发输出（前缀 `[NapCat]`）；最底下是「上次通知」卡片 |
| 通知群 | 群列表（启用 / 群号 / 备注 / 身份 / @方式）、启停、切换 @方式、自定义 @名单、删除、从 NapCat 拉取可用群 |
| 触发方式 | 直播间轮询、OBS 推流事件、进程检测三个开关，快捷键设置与进程名单，外加直播间隔与状态显示 |
| 消息与设置 | 群文案池、开播 / 下播 / 提醒 / 换游戏文案池、封面、游戏识别、二次提醒、换游戏冷却与确认时间、多群间隔、下播提示、启动行为，以及最下面的「测试」块（预览 / 私聊发开播 / 私聊发下播） |

> 这四页的名字**以源码为准**：`gui.py` 里 `TabStrip(self.root, ["运行日志", "通知群", "触发方式", "消息与设置"], …)`。
> 老文档里写的「通知哪些群」「通知内容与设置」是 1.1 时代的旧名字，代码里从来没有过这两个字符串。

### 10.3 热键捕获

「按下组合键设置…」弹出捕获窗，直接按键录入：

- 修饰键状态由 `KeyPress`/`KeyRelease` **手动跟踪**，不依赖 `event.state`
  （Windows 上 Alt 常常不进入 `state`，依赖它会导致漏判）
- 不支持无修饰键的单键组合
- 支持字母、数字、F1–F24
- 录入成功后提示「点保存并重新开始监控后生效」

### 10.4 NapCat 生命周期管理（由界面负责）

| 动作 | 行为 |
|---|---|
| 启动监控 | 检测 3000 端口 → 未就绪则以后台无窗口方式启动 NapCat → 最长等待 90 秒 → 再启动监控线程 |
| 停止监控 | 置停止事件 → 等监控线程退出 → 关闭 NapCat 与私有 QQ 实例 |
| 健康检查 | 监控运行期间每 8 秒检测 3000 端口；掉线则**自动重启 NapCat**，并重试一次 |
| 关闭窗口 | 弹窗三选：全部停止 / 仅关界面 / 取消 |

### 10.5 无窗口运行

NapCat 通过 `CREATE_NO_WINDOW` 启动（配合无 `pause` 的 `launcher-hidden.bat`），
其 stdout/stderr 由管道接入界面日志。用户不会看到任何黑色控制台窗口。

### 10.6 主题系统（浅色 / 深色）

**为什么是这个结构。** tkinter 的控件在**创建时**就把颜色写死进去了，之后没有
「重新着色」这条路。所以主题的做法只能是：

```
THEMES = {"light": {...}, "dark": {...}}      # 两份完整的调色板
apply_theme(name)                             # 把选中的那份写进模块全局
    ↓
App._peek_theme()  启动时先单独读一次 config.json 的 ui.theme
    ↓
_build_ui()        在主题已经定下来的前提下建界面
    ↓
App.toggle_theme() 换主题 → apply_theme() → rebuild_ui()
```

**启动顺序不能反。** `_peek_theme()` 必须在 `_build_ui()` **之前**跑。配置本来
要等界面建好后由 `reload_config()` 读，但那时颜色已经写死了 —— 晚一步就得整个
重建一次，启动时会明显闪一下。这是一个**故意违反"配置只在 reload_config 里读"
原则**的例外，所以它是个独立的 `@staticmethod`，读失败一律退回浅色。

**`rebuild_ui()` 要接回两样东西**，否则换主题会丢状态：

| 丢什么 | 怎么接回来 |
|---|---|
| 输入框里的内容 | `_cfg_to_ui()` —— 绝大多数内容本来就来自配置 |
| 日志面板里的文字 | `_log_tail` 内存缓冲 → `_restore_log()` |

当前状态（按钮文案、颜色）也要用 `_set_state(self.state)` 重新贴一次。

**颜色不许写死。** 除了 `THEMES` 两张表，`gui.py` 里不应再出现任何 `#rrggbb`
字面量。这条不是洁癖：1.2.0 之前复选框的 `selectcolor` 和输入框的
`fieldbackground` 都是写死的 `"white"`，浅色下看不出来，一切到深色就是几个
刺眼的白块 —— 而且是在**平时看不到的两个标签页**里，很容易漏。

**语义色分组。** 调色板按用途分，不按颜色分：

| 组 | 用途 |
|---|---|
| `BG` / `CARD` / `SUNKEN` / `BORDER` | 三层表面 + 分隔线 |
| `TEXT` / `MUTED` | 正文 / 次要文字 |
| `PRIMARY` / `PRIMARY_D` / `PRIMARY_S` | 主色的实心 / 按下 / 浅底 |
| `OK` / `WARN` / `BAD` + `_S` 浅底 | 状态语义 |
| `LOG_BG` / `LOG_FG` / `LOG_BAR` | 日志面板（两种主题下都保持深色） |

**深色主题的取法**参考 Flyme 夜间模式：深邃但不纯黑，且**层级越高面越亮**
（`BG` 最暗 → `CARD` 略亮）。主色在深底上要提亮一档，否则发闷。

## 11. 已识别的陷阱与对策

本节记录实现过程中实际踩到并修正的问题，是本规格中最具移植价值的部分。

### 11.1 触发与检测

| # | 陷阱 | 现象 | 对策 |
|---|---|---|---|
| T1 | 进程检测无法区分「开软件」与「开播」 | 准备工作期间误报 | 默认关闭，改用事件源 |
| T2 | B站直播姬真实进程名是 `livehime.exe` | 配成 `blivehime.exe` 时子串匹配永远失败 | 名单补全两种写法 |
| T3 | NapCat 群成员缓存竞态 | 刚登录时角色误判为 `member` | `resolve_role()` 全量复核 |
| T4 | `ctrl+alt+l` 在本机已被占用 | 热键静默失效 | 注册失败显式告警 + 实测空闲值 `ctrl+alt+k` |
| T5 | 启动时直播间已在直播 | 若补发，则每重启一次程序群友多收一条 | 初始状态只记录不触发 |
| T6 | 断流重连导致状态短暂变 0 | 误报「下播了」再「开播了」 | 离线宽限期（默认 60 秒）内恢复则取消 |
| T7 | 轮播（`live_status == 2`） | 被误判为「播完了」 | 归为离线但不触发下播通知 |

### 11.2 进程与系统集成

| # | 陷阱 | 现象 | 对策 |
|---|---|---|---|
| T5 | `Stop-Process -Name QQ -Force` 会杀掉用户自己的 QQ | 用户 QQ 被误关 | 仅按 `ExecutablePath` 过滤副本 |
| T6 | `NapCatWinBootMain.exe` 只认**裸** QQ 号码 | 传 `-q <号>` 被丢弃，退化为扫码登录 | 传裸号码，由其自行补 `-q` |
| T7 | `pythonw.exe` 下 `sys.stdout` 为 `None` | 所有 `print()` 抛异常 | 启动时补 `os.devnull` 黑洞流 |
| T8 | PyInstaller 打包后 `__file__` 指向解包临时目录 | 找不到 `config.json` / `napcat` | 冻结态改用 `sys.executable` 推导数据目录 |

### 11.3 网络

| # | 陷阱 | 现象 | 对策 |
|---|---|---|---|
| T9 | `urllib` 读取 Windows 注册表代理 | 发往 `127.0.0.1` 的请求被代理拦截，返回 `502` | `ProxyHandler({})` 强制直连 |
| T10 | NapCat WebUI 默认监听 `::`，且 `accessControlMode: "none"` | 局域网内任意设备可访问并控制机器人 | 改为 `127.0.0.1` + 64 位随机 token |
| T17 | 空间接口多发 `Accept` / `Accept-Language` | WAF 判为伪造请求，回 HTTP 412 `{"code":-412,"request was banned"}` —— 看着像"被限流了"，其实是**这一份请求**被拒 | 只发 `User-Agent` + `Referer`；`_selftest.py` 里有静态断言禁止把头"补全" |
| T18 | 短时间反复打空间接口 | **整个来源**一起 412（连 HTML 错误页），换个 UP 主也一样，要等它自己恢复 | 轮询按分钟算（默认 300 秒），`poll_seconds` 下限硬拦在 60；撞上之后退避 15 分钟（`SUB_BACKOFF_SECONDS`），不按原节奏接着敲 |

### 11.4 批处理（.bat）

| # | 陷阱 | 现象 | 对策 |
|---|---|---|---|
| T11 | cmd 按 OEM 代码页读取 .bat | UTF-8 中文导致**字节偏移错位**，注释碎片被当作命令执行 | `.bat` 一律保持纯 ASCII，中文只放在 Python 里 |
| T12 | `if (...)` 块内出现未转义的右括号 | 块被提前终止，`cmd` 在**解析期**即报 `was unexpected at this time`（条件为假也报） | 块内文案避免括号 |

### 13.3 图标生成

图标来自一张自绘插画（Q 版蓝发少女举黄色大喇叭喊「开播啦」），
用 `_build/_makeicon.ps1` 转成多尺寸 ICO：

- GDI+ `HighQualityBicubic` 缩放（Python 标准库没有图像缩放能力，用系统自带的 GDI+ 免装 Pillow）
- 圆角裁切（半径 = 边长 × 0.21，跟插画自带的圆角对齐），带 alpha 透明
- 输出 16/24/32/48/64/128/256 共 7 个尺寸，含 PNG 载荷
- 成品 `app.ico` 约 270 KB；仓库不放插画源图

> 圆角半径要**对着源图量**，不能照抄默认值：半径偏小会在四个角留下源图的白底
> 残边（深色任务栏上特别明显），偏大会把插画外圈那层高光描边切掉。
> 量法：沿顶边找彩色像素的起点 x，圆角半径 r ≈ x（把 0.14 改成实测比例即可）。

> **三个 PowerShell 坑**（脚本注释里也记了）：
> 1. 函数 `return` 数组会被自动展开，`byte[]` 变成 `object[]`，
>    导致 `BinaryWriter.Write` 找不到重载、静默写不进去 —— ICO 只有 118 字节（头部）。
> 2. 组装载荷时必须显式声明 `[byte[][]]`，否则 `+=` 同样会展开。
> 3. 脚本存成 **UTF-8 无 BOM** 时，Windows PowerShell 5.1 会按 ANSI 解码，
>    中文注释被拆坏后直接报 `Missing ')' in function parameter list`。
>    必须带 BOM（`UTF8Encoding($true)`）。

## 14. 已知限制

1. **仅 Windows**。依赖 Win32 进程枚举（`CreateToolhelp32Snapshot`）、
   `RegisterHotKey`，以及窗口枚举（`EnumWindows`，游戏识别用）。

2. **「OBS 推流事件」这一种触发方式只对 OBS 有效**。
   直播姬 / 直播伴侣不提供任何开播事件接口 —— 它们没有带 obs-websocket。
   **但这不影响能不能检测到你开播**：走「① 直播间开播时通知」那条路就行，
   它读的是平台判定的房间状态，跟你用什么软件（甚至手机开播）无关。
   §5.1 的触发源规格表把这两件事分开列了。

3. **游戏识别不是 100% 准**。它靠窗口标题、场景配置和平台清单推断，
   属于「猜」，不是权威数据。三类会失手的情况：
   - 游戏窗口标题是引擎名或空的，且不在场景字典 / 平台库里
   - 同时开多个游戏，优先级判断可能挑错
   - 反作弊游戏读不到 exe 路径，平台库那层对它们无效（靠窗口标题兜）

   `games.py` 的第 5 层（exe 版本信息）**尚未实现**，别指望它。
   认错了可以写进 `game.names`，多出来的可以写进 `game.ignore`。

4. **NapCat 版本敏感**。NapCat 需要与 QQ 构建版本匹配；QQ 自动更新后可能需要
   更新 NapCat。私有 QQ 副本的版本目录联接由 `_fix-qq-link.ps1` 在每次启动前
   自动重指，所以升级 QQ 本身不需要人工干预。

5. **存在账号风控风险**。NapCat 属第三方非官方协议端，建议使用小号。
   程序内置了开播冷却与二次提醒条数上限，但 `@全体成员` 用多了仍可能招人烦。

## 16. 文案系统（1.7.5 重做）

### 16.1 三层结构

| 层 | 是什么 | 在哪 |
|---|---|---|
| **模板** | 消息骨架：有哪几行、什么顺序 | `TEMPLATE_POOLS` + 配置里的 `templates` |
| **群文案** | 顶端那句勾人的话 | `HOOK_POOL` + 配置里的 `hooks` |
| **占位符** | 运行时填进去的值 | `render_text` 的 `fields` |

**群文案单独成池是有意的**：它跟模板的改动频率完全不同 —— 改一句开场白不该
逼着人重排整个模板。

### 16.2 时段：判断必须在"挑文案的那一刻"

写死时段一定出错（早上八点下播写成「今晚」）。所以：

- 基础池只放任何时刻都成立的句子
- 需要时段的放 `live_night` / `live_weekend` / `offline_night`
- `pick_from(pool, kind=...)` 在**每次挑文案时**按当前时间并入

**不能放在加载配置时算** —— 配置只读一次，而程序会一直挂着跨过 23 点、
跨过周末。

### 16.3 缺值处理：两种，别混

| 机制 | 行为 | 用在 |
|---|---|---|
| `DROP_LINE_WHEN_EMPTY` | 占位符为空时**整行消失** | `game` `peak` `title` `room_title` `room_desc` |
| `pick_from(avoid=...)` | 占位符为空时**整条模板排除** | `prev_game` |

区别在于"空"是常态还是意外：游戏名认不出来是常态，删掉那一行读起来是通的；
而「不玩《{prev_game}》了」如果整行删掉就什么都不剩了，所以该排除整条。

**别用假名字兜底。** 试过给 `prev_game` 填「刚才那个」，渲染出
「（刚才在玩《刚才那个》）」这种废话。

### 16.4 防抖 vs 冷却（换游戏）

两件不同的事，1.7.5 之前混成了一个：

| | 管什么 | 参数 |
|---|---|---|
| **确认时间** | 这游戏是不是**真的换了**（切窗口、加载地图会让标题瞬间变） | `game.change_settle_seconds`，默认 20 |
| **冷却** | 两条播报**别挨得太密** | `game.change_cooldown_minutes`，默认 0 |

原来的冷却只有后者，于是"玩 A 几分钟换 B"这种正常行为被当成刷屏压掉了。

### 16.5 直播间标题和公告

`BilibiliRoom.room_title()` 从 `room/v1/Room/get_info` 取 `data.title`；
`room_desc()` 取 `data.description` —— **接口给的是 HTML**（实测
`<p>…</p><br>`），必须剥标签、还原实体、压缩空白，否则群里会收到一堆尖括号。

**注意这两个函数一直存在，但 1.7.5 之前从没被调用过。** 占位符加了、
模板改了、数据线没接 —— 这种"改了但没生效"最难查，因为每一处单独看都是对的。

## 17. 托盘图标（1.7.5）

### 17.1 为什么自己写

pystray 会拖进 Pillow，光那一项就把单文件 exe 撑大十几兆。项目全体零依赖，
所以用 `ctypes` 直接调 `Shell_NotifyIcon`。

### 17.2 消息谁来泵

`Shell_NotifyIcon` 注册时要给一个窗口句柄，鼠标点击变成 `WM_` 消息发给它，
**而消息得有消息循环去取 —— Tk 只泵它自己的窗口。**

三条路：

| | 做法 | 结论 |
|---|---|---|
| a | 子类化 Tk 的窗口过程 | 要替换 Tk 的 WNDPROC，ctypes 回调写错就把 Tk 一起搞崩 |
| b | 自己建窗口塞进 Tk 的消息循环 | 做不到，Tk 不泵别人的窗口 |
| c | **自己开线程，建隐藏窗口 + 自己的 `GetMessage`** | ✅ 跟 Tk 完全隔离 |

选 c。托盘线程拿到点击后不能直接碰 Tk（Tk 不是线程安全的），回调统一走
`post()`（就是 `root.after`）丢回主线程。

### 17.3 ctypes 的宽度陷阱

```python
user32.DefWindowProcW(hwnd, msg, wparam, lparam)
# OverflowError: int too long to convert
```

`wintypes.WPARAM` / `LPARAM` 在 **64 位 Python 下仍是 32 位**，而真实的是
指针宽度。鼠标消息的 lparam 里塞着屏幕坐标，一超范围就炸。

**这是 ctypes 写 Win32 最经典的坑**：不声明 `argtypes` 就按默认宽度猜，
32 位下能跑，64 位下炸。现在用到的 Win32 函数都补了签名。

### 17.4 语义

- 点 X = **收进托盘，不退出**。这程序挂着才有用，点 X 多半是「别占我任务栏」
- 右键托盘 = 显示/隐藏、开始/停止监控、退出
- **退出只走托盘那一条**，误点不了

## 18. 界面绘制的性能

### 18.1 卡顿的真凶不是周期任务

先量了所有跑在主线程上的周期性活儿（`refresh_status` 每 400ms、
`_poll_processes` 每 3s、`_drain_log` 每 120ms…）—— **全都不贵，最贵 0.79ms**。
方向错了。

真凶是 `button_image`：**对整张圆角矩形逐像素跑 Python 循环。**

### 18.2 数字

```
_button_mask        72 ms    逐像素算覆盖率
PhotoImage + put   131 ms    往图片里塞 262 万字符
--------------------------
合计               208 ms / 张
拖窗口 x 12 张    = 846 ms / 帧
```

### 18.3 改法

**中间那一大片是纯色，不需要逐像素。** 只有四条边和四个角要按覆盖率混色。

改成「内核 `put(fill, to=...)` 一次填满 + 外圈逐像素」：
**208 → 47.5 ms**，再加 80ms 防抖（拖动过程不重画）。

### 18.4 两条走不通的路（记下来免得再走）

| 尝试 | 结果 |
|---|---|
| 「直边算一次铺一整条」 | ❌ 边界上相邻像素的覆盖率并不相同，错 1141 点 |
| 「按 r 缓存角块和边廓」 | ❌ 四个角的镜像映射对不上，错 2777 点（快 4 倍但画错了） |

**最后选的是已验证正确的那版。** 圆角画歪是肉眼可见的，而 47 ms 只发生在
拖动停下之后那一次。

验证方式：**215990 个像素逐一比对，0 处误差。**

       └─ 启动 HotkeyListener → 注册 ctrl+alt+k

用户停止推流 → ObsWatcher 记录状态，不发送

用户点「停止监控」
  └─ 置停止事件 → 监控线程退出 → 关闭控制端口
  └─ 终止 NapCat 与私有 QQ 实例（仅限 qq-napcat 路径）
